🔀 9Router 变更报告

v0.5.70 → v0.5.74 · 2026-09-08 · 仓库：lza6/9router-Max · 作者：9router 开发团队

1. 上下文（为什么做这些变更）

9Router 是已在生产环境部署使用的本地 AI 路由网关 + Next.js 仪表盘：一个 OpenAI 兼容端点（/v1/*）把流量路由到 40+ 上游 provider，带格式翻译、模型组合回退、多账号回退、OAuth/API key 凭据管理、token 刷新、配额统计。

本次迭代由五个核心诉求驱动：

  • 技能系统落地：让 AI 能"沉淀用户自己的 skills"（save_skill 语义），用得多=越信任。
  • 生产加固：项目已在生产跑，任何改动必须考虑兼容性、异常、并发、文档同步——不是"看起来能跑"，是"一次调用就通"。
  • 中文门面 + CI/CD：README 中文优先；建立从构建→质量→测试→安全→部署→回滚的完整流水线。
  • 借鉴顶级系统提示词：参考目录里的 CL4R1T4S（26 家厂商官方系统提示词全集）——提炼「先搜索再实现 / 负面清单 / 验证后完成 / 保密盾」等 10 维设计模式，灌入技能文件。
  • 性能与运维：限流、健康/就绪/指标探针、并发压测，向"能抗高并发"的成熟 SaaS 靠拢。

2. 直觉与设计思路

2.1 "用得多 = 越信任"的置信度模型

借鉴 agentmemory 的 reinforceLesson：每次成功使用 uses+1，confidence += 0.1×(1−confidence) 收敛到 1。用单条 SQL json_set 原子自增，保证并发不丢次数。列表按 uses 降序——用得多的技能排前面。

2.2 损坏数据 = 接口不崩

DB 里任何一条坏 JSON 都不该让整个技能列表 500。`rowToSkill` 用 try/catch 容错 + 字段类型强校验。

2.3 "负面清单"胜过"正面要求"

CL4R1T4S 提炼的最大教训：只告诉 agent 做什么不够，必须同等力度告诉它不做什么。最典型：video 技能「POST 绝不自动重试（会重复计费）」——从 prose 陈述改成显式「不要」指令。

2.4 黑匣子必须打开

Console Log 页（真实存在的 SSE 调试工具）在技能里零提及 = 能力被埋没。给每个技能加「排查」链路：看 status → 打开 Console Log → 看 error 字段。

2.5 默认关闭的加固

生产里最怕"升级即事故"。限流默认 RATE_LIMIT_ENABLED=false；CI 的 ESLint 保留 legacy 基线不阻塞；探针不探测付费上游避免误触配额。一切可回滚。

5. 诚实披露的边界

  • 未真实调用图片/视频生成等付费消耗型 API（按用户要求跳过）；参数拼装/负面清单已静态确认。
  • 未引入Redis/Kafka/消息队列/CDN——单机 SQLite 场景不需要，文档已写明何时才需要。
  • 横向扩展深挖（电商/媒体/PPT）两次子代理会话被中断无完整结果，路线图已记录但未实施。
  • P1 候选账号价值评分路由、流式无效响应抑制（思路已在参考的结果计划指南.md）。

6. 变更测验（你必须通过）

先自答，再展开看答案。

Q1. 「用得多=越信任」的置信度如何更新？
答案：每次成功使用 uses+1，confidence += 0.1×(1−confidence)（0.5→0.55→…），收敛到 1；用单条 SQL json_set 原子自增避免并发丢失。
Q2. 为什么 video 技能要写显式「不要」清单？
答案：因为创建 POST 自动重试会重复计费。从 prose 陈述改为显式负面指令，agent 超时也不会盲目重试。
Q3. 限流默认是开还是关？开启后超限返回什么？
答案：默认关闭（RATE_LIMIT_ENABLED=false，不改变现有生产行为）。开启后超限返回 429 + Retry-After。
Q4. /api/ready 为什么不探测上游付费 API？
答案：避免误触配额/计费；它只做 DB 可写探活。上游可达性由各 provider 的 test 端点覆盖。
Q5. 修复"损坏 JSON 炸列表接口"用了什么方法？
答案：rowToSkill 里 JSON.parse 包 try/catch，失败返回 null；getUserSkills 的 .filter(Boolean) 天然跳过坏行。
Q6. CI 的"无回归门禁"是什么？
答案：verify-no-regression.mjs 对比 known-fails.txt 基线——不产生新的基线外失败才通过（项目契约铁律）。
Q7. 真实 LLM E2E 为什么走 CONNECT 隧道而不是普通 fetch？
答案：本机代理对 curl/node-fetch 的 TLS 握手偶发 ECONNRESET；手动 CONNECT 隧道 + https.request 稳定。脚本读 E2E_API_KEY 环境变量，密钥不落库不入仓。
Q8. 损坏数据的 500 与业务校验 400 如何区分？
答案：route 层 catch 里白名单正则 /(required|exceeds)/i 命中则透出业务 400；其余一律收敛为通用「操作失败」500（不泄漏 DB 细节）。
